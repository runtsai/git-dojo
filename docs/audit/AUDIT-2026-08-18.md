## 2. Security Findings

### 2.1 HIGH — `requireOwner` middleware not applied to dojo check/bot endpoints

**Files:** `artifacts/api-server/src/routes/dojo.ts` lines 219, 269  
**Routes:** `POST /api/dojo/lessons/:lessonId/check`, `POST /api/dojo/lessons/:lessonId/bot`

The `requireOwner` middleware guards all capstone and crisis mutation endpoints but is absent from the two dojo routes that execute `check.sh` and `bot.sh` shell scripts. Any visitor who knows the URL can trigger these side-effectful operations (spawning child processes, writing to the filesystem, creating or mutating Git history in `~/git-dojo`). The `requireOwner` implementation explicitly allows workspace-internal calls (headers absent), so adding it here would not break CLI or test usage.

**Recommended fix:** Add `requireOwner` as the second argument to both `router.post(...)` calls, mirroring the pattern already used in `crisis.ts` lines 445 and 537.

---

### 2.2 MEDIUM — `lessonId` URL parameter used directly in file-system path without an allowlist check

**Files:** `artifacts/api-server/src/routes/dojo.ts` lines 147-228  
**Pattern:**
```
const lessonId = req.params.lessonId ?? "";
const lesson = root ? listLessonDirs(root).find((l) => l.id === lessonId) : undefined;
if (!lesson) { res.status(404)... }
const pgRoot = playgroundDir(root, lessonId);  // path.join(root, "playground", lessonId)
```

The `lesson` lookup against `listLessonDirs` acts as an implicit allowlist: the route only proceeds when `lessonId` matches a folder name that satisfies `LESSON_DIR_RE` (`/^lesson-(\d{2})-(.+)$/`). However the subsequent `path.join(root, "playground", lessonId)` uses the raw `lessonId` string, not the validated `lesson.id`. If `listLessonDirs` ever returns an entry whose `.id` value is attacker-controlled (e.g. from a tampered directory name), the validated object and the path-joined string would diverge. The current regex is strict enough to prevent `../` in the matched group, but this dual-path pattern is fragile.

**Recommended fix:** Replace `lessonId` with `lesson.id` (the validated value) in all `playgroundDir(root, ...)` calls.

---

### 2.3 LOW — Symlink escape guard in `readWorkingFileDiff` only covers the `untracked` branch

**File:** `artifacts/api-server/src/lib/repo-state.ts` lines 449-460

The symlink check (`lstatSync` + `realpathSync` containment) applies only when `entry.status === "untracked"`. Tracked files with status `staged`, `modified`, or `staged_and_modified` are passed directly to `git diff -- filePath`; git itself handles these safely (it reads blobs, not the working-tree path), so no live exploit exists. The asymmetry is a maintenance risk: a future code path that reads the working-tree file for a tracked entry would silently skip the symlink check.

**Recommended fix:** Document the assumption in a comment, or extract the symlink guard into a shared helper and call it unconditionally before any filesystem read.

---

### 2.4 LOW — No rate limiting on grader endpoints

**Files:** `artifacts/api-server/src/routes/dojo.ts`, `artifacts/api-server/src/routes/crisis.ts`

The check and bot endpoints spawn shell processes and run `git` commands. The `requireOwner` gap (2.1) makes this more acute, but even with auth restored, a valid owner could flood their own workspace. No request-level throttling is in place.

**Recommended fix:** Add a simple in-process rate limiter (e.g. `express-rate-limit`) on `/api/dojo/lessons/*/check`, `/api/dojo/lessons/*/bot`, and `/api/crisis/scenarios/*/check`.

---

### 2.5 INFO — `COMMIT_HASH_RE` allows short hashes (4 characters)

**File:** `artifacts/api-server/src/lib/repo-state.ts` line 361  
```ts
export const COMMIT_HASH_RE = /^[0-9a-f]{4,40}$/i;
```

Allowing 4-character abbreviated hashes means `git show <hash>` could match multiple objects if the repository ever becomes large enough. This is not a security issue in the current single-learner context but could cause ambiguous results. Consider raising the minimum to 7 characters to match GitHub's standard abbreviation length.

## 3. Architecture & Design Observations

### 3.1 Flat JSON persistence without transactional safety

`progress-store.ts`, `drill-store.ts`, and `capstone-store.ts` all use the read-parse-mutate-write pattern on JSON files. Concurrent requests (e.g. two `POST /check` calls within milliseconds) can produce a lost-update race. The design comment in `progress-store.ts` acknowledges the single-user assumption; the risk is low in practice but should be noted for any multi-user or multi-process upgrade.

### 3.2 PostgreSQL / Drizzle schema is a stub

`lib/db/src/schema/index.ts` exports only an empty object. The `DATABASE_URL` env var is listed as required in `replit.md`. If the app starts without a connected database, the Drizzle client will fail at the connection layer, but none of the current data paths use it — all persistence goes through the JSON stores. The schema stub should either be removed or developed before `DATABASE_URL` is declared required.

### 3.3 Legacy friction-record seeding may produce misleading trend data

**File:** `artifacts/api-server/src/lib/drill-store.ts` lines ~280-310

When a friction record has aggregate `failures`/`passes` totals but no `runs` window (records written before the rolling-window feature), the code reconstructs a synthetic `runs` array using Bresenham-style distribution. The synthetic entries all share the same `syntheticAt` timestamp, so the decay calculation (`exp(-k * age)`) will assign them zero decay for the first ~14 days and then all decay simultaneously. During that window the displayed `effectiveFailures` score may be artificially high. The comment in the code does not surface this to the UI.

### 3.4 `export.ts` is the largest non-test route (601 lines)

`artifacts/api-server/src/routes/export.ts` handles the lesson-export ZIP generation. It is 2× the size of the next largest route. No actionable issue found, but future contributors should be aware that changes here carry the highest complexity risk.

## 5. Code Quality Observations

### 5.1 `bot.sh` scripts have no timeout guard

**Files:** `git-dojo/lesson-08-the-collision/bot.sh`, `git-dojo/lesson-09-the-standoff/bot.sh`

The API server spawns these with a 15-second `timeout` in `mustGit`, but the bot scripts themselves can call external commands without an inner timeout. If a bot script hangs, the request will occupy a Node.js async slot for the full timeout window. Low risk, noted for completeness.

### 5.2 `DATA_DIR` path uses `process.cwd()` relative traversal

**Files:** All three `*-store.ts` files

```ts
const DATA_DIR = path.resolve(process.cwd(), "..", "..", "data");
```

This resolves to a `data/` directory two levels above the CWD when the server starts from `artifacts/api-server`. If the server is ever started from a different directory, the data path silently moves. Using an explicit env var (`DATA_DIR`, `DOJO_DATA_DIR`) or a path relative to `import.meta.url` would be more robust.

### 5.3 `crisis.ts` `crisisRoot()` falls back silently

**File:** `artifacts/api-server/src/routes/crisis.ts` lines ~24-31

If neither `~/git-dojo` nor the workspace-relative path exists, `crisisRoot()` returns the home path and the first `setup` call creates it. This is intentional but means a misconfigured deployment will silently create a new root rather than failing loudly. A startup health check that verifies (or pre-creates) the crisis root would make deployment issues visible earlier.

## 6. Dependency Observations

- **Supply-chain hygiene:** The 1-day minimum-release-age policy in `pnpm-workspace.yaml` is a well-documented, intentional defense. The `@replit/*` exclusion is scope-appropriate.
- **`esbuild` override:** The workspace pins `esbuild` to `0.27.3` to work around a vulnerability in `drizzle-kit`'s internal esbuild usage. This is correct but should be revisited when `drizzle-kit` ships a patched version.
- **No secrets found:** A scan of all committed source files found no API keys, tokens, or credentials in plaintext.
